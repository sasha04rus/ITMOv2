# Исходная спецификация команды UI: поиск подписчиков

Статус: независимый черновик до согласования с командой логики и человеком.
Фича: поиск по существующему списку подписчиков через простую веб-страницу.

## Основание и границы

Изучен существующий сервис из ветки `codex/practice-04`: `subscribe(name)` и `unsubscribe(name)` обрезают пробелы и отклоняют пустое имя; хранилище представляет собой `set` в памяти; `list_subscribers()` возвращает новый отсортированный список.

UI использует существующие данные, но не меняет их. В этой фиче нет добавления или удаления подписчиков с экрана, входа в аккаунт, базы данных, пагинации или внешних библиотек интерфейса. Исходные функции сервиса должны сохранить прежнее поведение. Отдельный сервер для фронтенда не требуется: HTML, JavaScript и API обслуживаются с одного origin.

## Пользовательская история

Как пользователь сервиса подписок, я хочу найти подписчика по части имени независимо от регистра, чтобы быстро увидеть нужные записи, включая имена на русском языке.

## Экран и действия

- Страница `/` содержит заголовок «Подписчики», связанный с полем ввода label «Поиск по имени», кнопки «Найти» и «Сбросить», область состояния и список результатов.
- При открытии страницы выполняется поиск с пустой строкой: показываются все имеющиеся подписчики.
- Enter в поле и кнопка «Найти» выполняют одинаковое действие. Автоматический поиск при каждом символе и debounce не нужны.
- «Сбросить» очищает поле, возвращает фокус в поле и запрашивает полный список.
- Имена выводятся как текст, а не HTML. UI сохраняет порядок, полученный от API.
- Статус загрузки и результат доступны через live region; поле и кнопки доступны с клавиатуры.

## Состояния

| Состояние | Что видит пользователь |
|---|---|
| Loading | «Загрузка…»; прежние результаты скрыты, чтобы их нельзя было принять за новый ответ. |
| Success | Полученный список и количество найденных записей. |
| Empty | «Ничего не найдено»; пустой результат не считается ошибкой. |
| Error | Понятное сообщение об ошибке и кнопка «Повторить». Устаревшие результаты скрыты. |

Повторный запрос заменяет предыдущий: ответ на старый поиск не должен перезаписать более новый результат. Во время загрузки можно изменить строку и отправить новый поиск. «Повторить» повторяет последний отправленный запрос, а не произвольно изменённый текст в поле.

## Предлагаемый контракт UI -> логика

### Запрос

`GET /api/subscribers?q=<строка, закодированная как URL query parameter>`

- `q` можно опустить; отсутствие и пустая строка означают полный список.
- Пробелы по краям строки не участвуют в поиске.
- Ищется подстрока имени без учёта регистра для русского и латиницы.
- Предлагаемый предел: 100 Unicode code points после обрезки пробелов; длина проверяется сервером.
- UI отправляет запрос на свой origin, без CORS-настроек и токенов.

### Успешный ответ: HTTP 200, JSON

```json
{
  "items": ["ALINA", "Alice"],
  "total": 2,
  "query": "ali"
}
```

Пример описывает форму ответа; конкретный набор имён определяется правилом поиска. `items` — массив строк без изменения исходного написания имён; `total` — число элементов результата, то есть `items.length`; `query` — применённая строка после обрезки пробелов. Порядок определяет backend. Пустой ответ имеет `items: []` и `total: 0`.

### Ошибочный вход: HTTP 400, JSON

```json
{
  "error": {
    "code": "query_too_long",
    "message": "Поисковый запрос должен быть не длиннее 100 символов."
  }
}
```

UI показывает сообщение от API как обычный текст. Для сетевой ошибки, HTTP 5xx или некорректного формата ответа UI показывает «Не удалось загрузить подписчиков. Попробуйте ещё раз» и предлагает повторить запрос. Внутренний текст исключения и stack trace пользователю не показываются.

## Критерии приёмки и сценарии

### UI-AC-01. Начальный список и сброс

**Given** в сервисе есть несколько подписчиков, **When** пользователь открывает страницу, **Then** выполняется запрос без фильтра и показывается полный список в порядке backend.

**Given** пользователь уже выполнил поиск, **When** он нажимает «Сбросить», **Then** поле очищается, фокус возвращается в поле, а список снова соответствует запросу без фильтра.

### UI-AC-02. Поиск по русским и латинским именам

**Given** в сервисе есть `Alice` и `Анна`, **When** пользователь ищет ` ALI `, **Then** показана `Alice`, а при поиске `АН` показана `Анна`.

**Given** одинаковый текст в поле, **When** поиск отправляется через Enter или «Найти», **Then** результат и состояние совпадают.

### UI-AC-03. Пустой результат и загрузка

**Given** отправлен новый поиск, **When** ответ ещё не получен, **Then** видна загрузка, а прежний список скрыт.

**Given** API вернул пустой массив, **When** ответ обработан, **Then** показано «Ничего не найдено», ошибка не показывается.

### UI-AC-04. Ошибка и восстановление

**Given** запрос длиннее согласованного предела, **When** сервер вернул HTTP 400 с `query_too_long`, **Then** UI показывает понятное сообщение, не зависает в состоянии загрузки и позволяет исправить запрос.

**Given** произошла сетевая ошибка или HTTP 5xx, **When** пользователь нажимает «Повторить» после восстановления сервера, **Then** повторяется последний отправленный поиск и показывается его результат.

### UI-AC-05. Безопасное и последовательное отображение

**Given** имя содержит HTML-подобный текст, **When** оно отображается, **Then** текст виден буквально и не исполняется как разметка или скрипт.

**Given** старый запрос завершился позже нового, **When** получены оба ответа, **Then** экран показывает только результат последнего отправленного поиска.

## Открытые вопросы для согласования

1. Принимает ли команда логики форму `items: string[]`, `total` как количество совпадений и `query` как применённый фильтр? Если нужен общий размер хранилища, для него требуется отдельное имя поля.
2. Достаточен ли предел в 100 Unicode code points после trim? Ошибку следует согласовать до реализации UI и API.
3. Как обеспечим воспроизводимые исходные данные для демо и сквозных тестов, сохранив хранение в памяти и не добавляя редактирование в UI?
4. Подтверждается ли простое правило поиска: регистр не учитывается, но транслитерация, исправление опечаток и приравнивание `е`/`ё` не выполняются?
5. Как поступаем при повторяющемся параметре `q` в URL: отклоняем неоднозначный запрос или используем одно значение? UI сам такие запросы не создаёт.

## Компромиссы и проверка

Явная кнопка поиска проще автоматических запросов и делает загрузку/ошибку наблюдаемыми. Отсутствие добавления и удаления на экране удерживает границы одной фичи; вопрос наполнения данных остаётся частью согласования. UI доверяет серверу порядок и правила сравнения, чтобы не создавать вторую реализацию поиска в браузере.

Предлагаемая проверка: браузерный сквозной сценарий «открыть -> найти -> получить пустой результат -> сбросить», отдельные проверки HTTP 400, сетевого сбоя и устаревшего ответа. Это план проверки: реализация и тесты в рамках этого независимого черновика не выполнялись.
