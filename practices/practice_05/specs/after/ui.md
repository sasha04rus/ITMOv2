# Спецификация команды UI после сверки: поиск подписчиков

Статус: редакция команды UI после сверки с командой логики и общим контрактом; контракт утверждён пользователем 2026-10-26 до реализации. Это спецификация до реализации, а не отчёт о завершённой разработке или тестировании.

Основания: неизменённые `../before/ui.md`, `../before/logic.md`, `../coordination.md` и общий контракт `../001-subscriber-search/contracts/http.md`. При последующих изменениях контракта обе команды должны синхронно пересмотреть спецификации.

## User Scenarios & Testing

### User Story 1 — найти подписчика (P1)

Пользователь открывает страницу существующего сервиса и находит подписчиков по части имени без учёта регистра. Русский текст и латиница поддерживаются без транслитерации.

**Independent Test:** запустить сервер с `--demo`, открыть `/`, найти `  ALI  ` и `АН`, затем очистить поиск.

**Acceptance Scenarios:**

1. **Given** сервер запущен с `--demo`, **When** открывается `/`, **Then** видны `Alice`, `Bob`, `Анна`, `Борис` в порядке backend и число совпадений 4.
2. **Given** четыре демонстрационных имени, **When** пользователь вводит `  ALI  ` и нажимает «Найти», **Then** видна только `Alice`, число совпадений 1; пробелы убирает сервер.
3. **Given** те же данные, **When** пользователь вводит `АН` и нажимает Enter, **Then** видна только `Анна` с исходным написанием имени.
4. **Given** применён непустой фильтр, **When** пользователь нажимает «Сбросить», **Then** поле очищается, получает фокус, и загружаются все четыре имени.

### User Story 2 — различать пустой результат и ошибку (P1)

Пользователь понимает, что отсутствие совпадений является нормальным результатом, а при некорректном запросе или недоступности сервера может исправить запрос либо повторить его.

**Independent Test:** проверить пустой запрос на сервере без `--demo`, отсутствующее имя на сервере с `--demo`, запросы длиной 100/101 code points и восстановление после сетевой ошибки.

**Acceptance Scenarios:**

1. **Given** сервер с `--demo`, **When** поиск `zzz` возвращает HTTP 200 с пустым `items`, **Then** показано «Ничего не найдено», а не ошибка.
2. **Given** сервер запущен без `--demo`, **When** открыта страница, **Then** пустое хранилище отображается тем же корректным пустым состоянием.
3. **Given** ввод из 100 букв `x`, **When** пользователь отправляет поиск, **Then** запрос принимается сервером и UI показывает пустой результат, а не ошибку длины.
4. **Given** ввод из 101 буквы `x`, **When** сервер отвечает HTTP 400 с `query_too_long`, **Then** UI показывает `error.message` как текст, прекращает загрузку и позволяет отправить исправленный запрос.
5. **Given** запрос завершился сетевой ошибкой, **When** пользователь нажимает «Повторить» после восстановления связи, **Then** повторяется последний отправленный запрос, даже если текст в поле успел измениться.

### User Story 3 — получать актуальный и безопасный результат (P2)

Пользователь может отправить новый поиск до завершения старого и взаимодействовать с формой с клавиатуры. Строки, полученные от API, не интерпретируются как HTML.

**Independent Test:** задержать первый ответ в браузерном тесте, отправить второй запрос, вернуть ответы в обратном порядке; отдельно проверить имя с HTML-подобным текстом и доступность формы с клавиатуры.

**Acceptance Scenarios:**

1. **Given** старый запрос ещё выполняется, **When** отправлен новый, **Then** UI показывает загрузку нового запроса, а старый ответ или старая ошибка не изменяют новое состояние.
2. **Given** API вернул имя `<b>Alice</b>`, **When** список отображён, **Then** угловые скобки и тег видны как текст, а элемент `b` из имени не создаётся.
3. **Given** пользователь работает только с клавиатурой, **When** он переходит по форме и отправляет поиск, **Then** доступны поле, «Найти», «Сбросить» и условная кнопка «Повторить»; статус объявляется через live region.

## Requirements

### Functional Requirements

- **UI-FR-001:** `/` MUST содержать заголовок «Подписчики», поле с label «Поиск по имени», кнопки «Найти» и «Сбросить», область состояния и список результатов. HTML и JavaScript обслуживаются с того же origin, что и API; npm-зависимости не требуются.
- **UI-FR-002:** открытие страницы MUST отправлять `GET /api/subscribers` для полного списка. Поиск MUST использовать единственный URL-параметр `q`, сформированный средствами URL encoding. Enter и кнопка «Найти» MUST отправлять один и тот же запрос. Автоматического поиска при каждом нажатии клавиши нет.
- **UI-FR-003:** UI MUST передавать исходную строку поля без собственной нормализации Python `str.strip()`, изменения регистра и подсчёта допустимой длины. Нельзя ограничивать поле через `maxlength=100`: браузерная длина может измеряться в UTF-16 code units, а контракт определяет серверный предел в 100 Unicode code points после `strip()`.
- **UI-FR-004:** для HTTP 200 UI MUST принимать объект `query: string`, `items: string[]`, `total: integer`, где `total >= 0` и `total === items.length`. `query` содержит применённую сервером строку с сохранением её регистра. UI MUST сохранять порядок и написание `items`, не сортируя и не фильтруя их повторно.
- **UI-FR-005:** начальный запрос и сброс MUST возвращать полный список. Сброс MUST очистить поле, вернуть туда фокус и заменить предыдущий запрос новым запросом без фильтра. UI не изменяет хранилище подписчиков.
- **UI-FR-006:** `loading` MUST показывать «Загрузка…» и скрывать предыдущие результаты; `success` MUST показывать список и `total`; `empty` MUST показывать «Ничего не найдено»; `error` MUST показывать сообщение и кнопку «Повторить». Только результат последнего отправленного запроса может менять состояние.
- **UI-FR-007:** HTTP 400 с корректным объектом `error.code`/`error.message` MUST показывать `error.message` как обычный текст. `query_too_long` означает превышение 100 code points после серверного trim; `invalid_query` означает повторный/неизвестный параметр или некорректную UTF-8 query string. UI сам не создаёт повторных или неизвестных параметров.
- **UI-FR-008:** сетевая ошибка, HTTP 5xx и некорректный JSON или его форма MUST переводить UI в состояние ошибки с сообщением «Не удалось загрузить подписчиков. Попробуйте ещё раз» и возможностью повтора. Неожиданный HTTP-ответ, например 404/405 из-за несовместимого URL/метода клиента, также не должен оставлять загрузку бесконечной или отображаться как пустой список.
- **UI-FR-009:** «Повторить» MUST повторять последнюю отправленную строку, а не текущее несохранённое содержимое поля. Новая отправка и сброс MUST иметь приоритет над более старыми ответами; механизм можно реализовать идентификатором запроса и/или отменой, но отмена старого запроса не должна показываться как ошибка нового.
- **UI-FR-010:** имена, сообщения API и значения состояния MUST выводиться текстовыми DOM-операциями. Label MUST быть связан с полем; элементы MUST работать с клавиатуры; область статуса MUST объявлять изменения через live region.

### Shared Data and Constraints

| Элемент | Согласованное для этой редакции значение |
|---|---|
| API | `GET /api/subscribers`, необязательный единственный `q` |
| Ответ успеха | `query`, `items`, `total`; `total` равен длине `items` |
| Поиск | Unicode `casefold()` и подстрока; `е`/`ё` различаются |
| Сортировка | Прежний Python `sorted` по исходным именам; UI не пересортировывает |
| Пустой запрос | Полный список, включая строку из пробелов после серверного trim |
| Граница | 100 Unicode code points после `strip()` принимаются; 101 даёт `400 query_too_long` |
| Структура параметров | Повторный `q` или неизвестный параметр даёт `400 invalid_query` |
| Демо | `--demo` создаёт Alice, Bob, Анна, Борис; без флага список пуст |
| Хранение | Память процесса; перезапуск не сохраняет подписчиков |

### Out of Scope

Добавление/удаление подписчиков из UI, новые HTTP-операции записи, БД, авторизация, пагинация, нечёткий поиск, транслитерация, Unicode NFC-нормализация, приравнивание `е`/`ё`, автоматические запросы при вводе и изменение прежних функций сервиса не входят в фичу.

## Success Criteria

- **UI-SC-001:** воспроизводимый браузерный сценарий «открытие с `--demo` -> поиск латиницы -> поиск кириллицы -> пустой результат -> сброс» подтверждает переход UI -> API -> логика -> UI.
- **UI-SC-002:** граничные запросы 100/101 code points различаются по контракту, ошибка видна пользователю, а последующий корректный поиск восстанавливает успешное состояние.
- **UI-SC-003:** отдельный сценарий сетевого сбоя подтверждает понятную ошибку и повтор именно последнего отправленного запроса.
- **UI-SC-004:** управляемая задержка старого ответа и HTML-подобное имя подтверждают актуальность и текстовый вывод данных.
- **UI-SC-005:** сценарии проверки и общий контракт не требуют изменений старых `subscribe`, `unsubscribe`, `list_subscribers` и не добавляют операции записи через HTTP.

Это условия будущей проверки, а не утверждение об их прохождении. Решение о принятии контракта человеком и фактические результаты реализации фиксируются отдельно.

## Что изменилось после сверки

1. Серверный лимит конкретизирован как 100 Unicode code points после Python `strip()`; клиентская проверка, способная расходиться с сервером, исключена.
2. Разделены ошибки длины (`query_too_long`) и структуры параметров (`invalid_query`); повторные и неизвестные параметры отклоняются.
3. `total` однозначно означает количество совпадений, а не размер хранилища до фильтрации.
4. Порядок результатов связан с прежней сортировкой Python; регистр имён и порядок UI сохраняет.
5. Воспроизводимое наполнение решено флагом `--demo` с четырьмя именами; пустое хранилище без флага остаётся корректным состоянием.
6. Уточнены `casefold`, различие `е`/`ё`, отсутствие транслитерации и NFC-нормализации.

## Проверка реализуемости и замечания

Спецификация реализуема обычными HTML/JavaScript и same-origin JSON API без библиотек. Загрузка, повтор и игнорирование устаревшего ответа не требуют расширения контракта. Массив строк достаточен для отображения read-only списка; отдельные идентификаторы для операций редактирования здесь не нужны.

Противоречий общему контракту в этой редакции не обнаружено. Для будущих тестов обработка 400 `invalid_query` проверяется прямым HTTP-запросом или подменой ответа: штатная форма не должна создавать заведомо некорректную структуру URL. Проверку предела нельзя подменять browser `maxlength`, иначе сценарий 101 символа не достигнет API. HTTP 500 не требует придумывать новый стабильный код ошибки backend: UI использует общий сценарий сбоя.

Человеческое утверждение этой редакции и общего контракта пока ожидается; реализация не начиналась.
