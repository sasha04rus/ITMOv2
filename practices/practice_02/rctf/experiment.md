# R.C.T.F.

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- **Role:**
  Ты — ведущий продуктовый аналитик и QA-инженер, проверяющий критерии приёмки помощника ревьюера PR.
- **Context:**
  Используй только practices/practice_01/context.md, problem.md, product_management.md, tests_e2e.md и TRAINING_PR.diff. В артефакте уже есть позитивный, негативный и граничный сценарии. Нужно проверить их согласованность, наблюдаемость и связь с evidence. Не придумывай HTTP-статусы, максимальный размер diff, SLA и отсутствующие требования.
- **Task:**
  Проверь три сценария и найди:
  1. неоднозначные или непроверяемые формулировки;
  2. смешение текущего поведения AS IS и желаемого TO BE;
  3. утверждения без источника;
  4. несоответствия между product_management.md и tests_e2e.md.
  После этого предложи уточнённые версии трёх Gherkin-сценариев. Не выдавай предлагаемые требования за подтверждённые факты.
- **Format:**
  1. Таблица «Сценарий / проблема / evidence / предлагаемое уточнение».
  2. Три уточнённых Gherkin-сценария.
  3. Список подтверждённых положений.
  4. Список открытых вопросов.
  5. Список предлагаемых изменений с указанием файла и раздела.

2) Уточнённые Gherkin-сценарии

```gherkin
Feature: Помощник ревьюера PR по unified diff

  Scenario: Позитивный — корректный unified diff → структурированный отчёт
    Given на вход передан текст в формате unified diff (с заголовками @@ и путями файлов), пригодный для парсинга
      And в diff присутствуют один или более хунков изменений
    When помощник анализирует diff
    Then полный отчёт содержит разделы: "Описание", "Риски" (не более 3 пунктов) и "Проверки"
      And каждый пункт раздела "Риски" содержит evidence: путь к файлу и координаты из заголовка хунка @@ -x,y +u,v @@ или точный фрагмент хунка
      And координаты хунка не выдаются за номера строк исходного файла

  Scenario: Негативный — отсутствует поле diff в payload
    Given входной объект не содержит поля "diff"
    When помощник пытается выполнить анализ
    Then в разделе "Описание" зафиксировано, что анализ невозможен без поля "diff"
      And конкретный HTTP-статус не указывается — отмечено как открытый вопрос

  Scenario: Граничный — найдено > 3 потенциальных проблем и часть утверждений без evidence
    Given на вход передан корректный unified diff
      And по результатам анализа найдено более трёх потенциальных проблем
      And часть утверждений не имеет достаточного evidence
    When помощник формирует итоговый отчёт
    Then раздел "Риски" содержит не более трёх пунктов (самые значимые)
      And оставшиеся проблемы и/или неподтверждённые утверждения вынесены в "Открытые вопросы" или помечены как "потенциальный риск/гипотеза"
      And evidence для каждого пункта содержит путь к файлу и координаты хунка или точный фрагмент этого хунка
```

3) Подтверждённые положения
- Используем единственный источник анализа — фактический unified diff.
- Структура отчёта: «Описание», «Риски» (≤ 3), «Проверки».
- «Без evidence — не дефект»: маркируем как риск/гипотеза или в открытые вопросы.
- Evidence = путь и координаты хунка (из @@ … @@) или точный фрагмент; координаты ≠ номера строк исходника.
- HTTP-статус не задан источниками (открытый вопрос).

4) Открытые вопросы
- Что делать при пустом diff/отсутствии хунков?
- Как ранжировать «наиболее значимые» ≤ 3 риска?
- Где располагать «Открытые вопросы» в отчёте?

5) Предлагаемые изменения (не внесены)
- practices/practice_01/product_management.md → «User stories и acceptance criteria»: внести оговорки по формату unified diff входа, источнику координат хунка, правилам отбора ≤ 3 рисков и размещению остальных как открытых вопросов/гипотез.
- practices/practice_01/tests_e2e.md → таблица: синхронизировать формулировки наблюдаемых результатов и подтверждений с обновлёнными сценариями.

## Что изменили в исходном артефакте

- Файл и раздел:
  - practices/practice_01/product_management.md → «User stories и acceptance criteria»;
  - practices/practice_01/tests_e2e.md → таблица E2E.
- Изменение:
  - Зафиксированы требования TO BE: структура отчёта («Описание», «Риски» ≤ 3, «Проверки»); evidence = путь + координаты из заголовка хунка @@ -x,y +u,v @@ или точный фрагмент; координаты ≠ номера строк исходника.
  - Позитивный: минимальные признаки unified diff (заголовки файлов и ≥1 хунк) описаны как TO BE.
  - Негативный: разделены AS IS (ошибка при обращении к payload["diff"] до отчёта) и TO BE (отчёт не формируется; формат ответа и HTTP-статус — открытые вопросы).
  - Граничный: в «Риски» попадают ≤ 3 утверждения с наиболее сильным evidence; неподтверждённые — не входят в «Риски», а добавляются как предлагаемые проверки в «Проверки».
- Как проверили:
  - make -C practices/practice_02 test → «Practice 2 artifacts: OK».
- Что отклонили:
  - Сообщение при отсутствии diff в «Описание» — отклонено: отчёт не формируется при таком входе.
  - Формулировка «самые значимые» — отклонена, критерий значимости не определён; используем «наиболее сильное evidence».
  - Добавление раздела «Открытые вопросы» — отклонено, оставляем только «Описание», «Риски», «Проверки».
  - Утверждение о проверке/парсинге unified diff как уже реализованном факте — отклонено; это TO BE.
