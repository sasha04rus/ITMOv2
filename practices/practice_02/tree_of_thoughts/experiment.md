# Tree of Thoughts

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- Решение, для которого нужны альтернативы:
  Как помощник должен выбирать не более трёх пунктов для раздела «Риски», если при анализе diff найдено больше трёх кандидатов.
- Критерии выбора:
  1. Доказательность по diff.
  2. Воспроизводимость выбора другим инженером.
  3. Минимальный риск выдуманной severity.
  4. Простота проверки.
  5. Совместимость с product_management.md и tests_e2e.md.

## Запрос

"Tree of Thoughts for PR-review assistant

Context:
- анализ выполняется только по unified diff;
- утверждения без достаточного evidence не включаются в «Риски»;
- раздел «Риски» содержит не более трёх пунктов;
- бизнес-критичность и severity могут быть неизвестны по одному diff;
- нельзя придумывать сведения, отсутствующие в diff;
- текущая формулировка «наиболее сильное evidence» требует более точного и воспроизводимого правила.

Goal:
- Предложить минимум три альтернативы выбора ≤ 3 пунктов «Рисков», когда кандидатов больше трёх.

Alternatives to consider:
 A. Evidence-first: отбирать по силе evidence; точный изменённый фрагмент сильнее одной координаты хунка, координата сильнее общей ссылки только на файл. При равенстве использовать порядок появления в diff.
 B. Severity-first: выбирать предполагаемые наиболее критичные проблемы по влиянию на систему.
 C. Комбинированная: сначала допускать только кандидатов с evidence, затем оценивать их по evidence и предполагаемому влиянию.

For each alternative provide:
- плюсы;
- минусы;
- оценку по каждому критерию (1–5);
- какие новые предположения потребуются;
- как вариант будет отражён в Gherkin и E2E-проверке.

Finally select one alternative and explain the choice. Это предлагаемое требование TO BE; не выдавай его за реализованное поведение. Опиши способ проверки.
"
## Варианты решения

### Новые предположения по альтернативам

- A. Evidence-first:
  - Ввести формальный порядок силы evidence: «путь + точный изменённый фрагмент» > «путь + координаты хунка».
  - Правило tie-breaker: при равной силе evidence использовать порядок появления кандидатов в diff.
  - Общая ссылка только на файл не считается достаточным evidence.

- B. Severity-first:
  - Нужны правила оценки критичности/влияния вне diff (доменные знания, SLA, метрики воздействия) — отсутствуют в контексте.
  - Допускается субъективная интерпретация влияния, что противоречит ограничениям.

- C. Комбинированная:
  - Требует и формального порядка evidence, и правил оценки влияния (как в B), что добавляет непроверяемые допущения.

### Отражение в Gherkin и E2E

- A. Evidence-first:
  - Gherkin (граничный сценарий, TO BE): обязательный фильтр достаточного evidence (только «путь + фрагмент» или «путь + координаты»), затем сортировка по силе evidence; при равенстве — по порядку в diff; взять первые три. Кандидаты с ссылкой только на файл исключаются из «Рисков» и конвертируются в предлагаемые проверки в «Проверки».
  - E2E: кейс с > 3 кандидатами разного типа evidence; ожидать, что в «Риски» попали три по правилу, а file-only кандидаты отсутствуют и отражены в «Проверках» как предлагаемые проверки.

- B. Severity-first:
  - Gherkin/E2E потребуют правил оценки severity, источников подтверждения — отсутствуют в diff; приведёт к выдумкам и низкой воспроизводимости.

- C. Комбинированная:
  - Gherkin/E2E должны зафиксировать и порядок evidence, и шкалу влияния; без источников для влияния сценарии станут непроверяемыми.

## Выбор

- Выбранная альтернатива: A. Evidence-first (предлагаемое требование TO BE)
- Почему:
  - максимальная опора на доступные источники (unified diff);
  - высокая воспроизводимость между инженерами;
  - минимизирует риск выдуманной severity;
  - полностью совместима с текущими product_management.md и tests_e2e.md.
- Правило (уточнённое):
  1) Обязательный фильтр достаточного evidence: кандидат допускается в «Риски» только если содержит либо «путь + точный изменённый фрагмент хунка», либо «путь + координаты хунка». Общая ссылка только на файл — недостаточна; такой кандидат исключается из «Рисков» и конвертируется в предлагаемые проверки раздела «Проверки».
  2) Если после фильтра осталось 0–3 кандидатов — в «Риски» включаются все допущенные кандидаты.
  3) Если после фильтра осталось > 3 кандидатов — среди допущенных порядок: «путь + точный изменённый фрагмент» > «путь + координаты хунка». При одинаковой силе evidence — порядок появления в diff. В «Риски» берутся первые три кандидата.
- Как проверим:
  - Gherkin (TO BE) дополнить уточнённым правилом отбора (фильтр; при ≤3 — все; при >3 — сортировка и top-3).
  - В tests_e2e.md зафиксировать кейсы: (а) ≤3 допущенных — все включены; (б) >3 допущенных — включены первые три по правилу; file-only кандидаты — в «Проверки» как предлагаемые проверки.
