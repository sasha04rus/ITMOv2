# Few-shot

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- Артефакт Практики 1: practices/practice_01/product_management.md
- Что хотим улучшить:
  - сценарии Given/When/Then недостаточно конкретны;
  - негативный сценарий не определяет точный наблюдаемый результат;
  - граничный сценарий не содержит измеримой границы;
  - не везде понятно, чем подтверждается ожидаемое поведение.

## Примеры

### Хороший результат

```gherkin
Feature: Помощник ревьюера PR по unified diff

  Scenario: Позитивный — корректный unified diff даёт структурированный отчёт
    Given на вход передан корректный unified diff в текстовом формате
      And в diff присутствуют хунки по файлам "app/review_service.py" и "app/api.py"
    When помощник анализирует diff
    Then он возвращает структурированный отчёт из не более чем 3 пунктов
      And каждый пункт содержит проблему и ссылку на соответствующий хунк (путь к файлу и изменённые строки)
      And утверждение без ссылки на diff-хунк помечается как "potential", а не как доказанный дефект
```

### Плохой результат

```gherkin
Feature: Проверка PR

  Scenario: Ревью без деталей
    Given есть какой-то PR
    When помощник его проверяет
    Then помощник пишет комментарии
    # Нет требований к формату diff, к структуре отчёта и доказательствам; шаги нельзя проверить
```

## Запрос

"Ты — продуктовый аналитик и QA. Используй контекст только из practices/practice_01/context.md, practices/practice_01/problem.md, practices/practice_01/product_management.md, practices/practice_01/tests_e2e.md и фактический unified diff из practices/practice_01/TRAINING_PR.diff. Сначала посмотри два примера acceptance criteria: хороший (конкретный Gherkin для анализа PR по unified diff) и плохой (расплывчатый сценарий без проверяемых шагов).

Задача: написать для помощника ревьюера PR три сценария в формате Gherkin:
- Позитивный: на вход передан корректный unified diff; на выходе — структурированный отчёт с не более чем 3 пунктами, и каждый пункт содержит ссылку на соответствующий хунк (путь к файлу и изменённые строки) как evidence.
- Негативный: поле diff в входном объекте отсутствует; текущая ошибка должна быть подтверждаема по diff/реализации (не придумывай желаемый HTTP-статус — если он неизвестен по источникам, отметь как открытый вопрос).
- Граничный: найдено больше трёх потенциальных проблем и/или часть утверждений не имеет evidence в diff; итог должен содержать не более трёх пунктов, а утверждение без evidence нельзя называть доказанным дефектом.

Не придумывай максимальный размер diff, HTTP-статусы, SLA, консольные команды или другое поведение, отсутствующее в источниках. Неизвестное явно помечай как открытый вопрос. Формат вывода: три Gherkin-сценария + краткие пояснения, на какие хунки TRAINING_PR.diff ссылается evidence."

## Что получили

```gherkin
Feature: Помощник ревьюера PR по unified diff

  Background:
    # Источники: practices/practice_01/TRAINING_PR.diff и шаблоны практики 1
    Given анализ выполняется только по фактическому unified diff

  Scenario: Позитивный — корректный unified diff → структурированный отчёт ≤ 3 пункта
    Given на вход передан корректный unified diff
      And diff содержит хунки по файлам "app/review_service.py" и "app/api.py"
    When помощник формирует отчёт
    Then отчёт содержит не более трёх пунктов
      And каждый пункт содержит проблему и ссылку на соответствующий хунк (путь к файлу и изменённые строки)
      And утверждение без ссылки на diff-хунк помечается как "potential"

  Scenario: Негативный — отсутствует поле diff в payload
    Given входной объект не содержит поля "diff"
    When помощник пытается выполнить анализ
    Then фиксируется текущая ошибка, подтверждаемая по реализации, что без поля "diff" анализ невозможен
      And желаемый HTTP-статус не указывается (отмечено как открытый вопрос)

  Scenario: Граничный — найдено > 3 потенциальных проблем и часть утверждений без evidence
    Given на вход передан корректный unified diff
      And по результатам анализа найдено более трёх потенциальных проблем
      And часть утверждений не подтверждается ссылками на diff-хунки
    When помощник формирует итог
    Then итоговый отчёт содержит не более трёх пунктов, а утверждения без evidence помечены как "potential", а не как доказанные дефекты
```

Пояснения и ссылки на evidence из TRAINING_PR.diff:
- app/api.py: строки хунка с добавлением `create_review(payload: dict)` и обращением `payload["diff"]` — подтверждают негативный сценарий (отсутствие поля ведёт к ошибке). В diff это строки 35–38 нового кода.
- app/review_service.py: хунк с методом `review(self, diff: str)` и формированием `prompt = f"Review this pull request and find problems:\n{diff}"` — источник для анализа и ссылок на хунки.
- Ограничение по количеству пунктов (≤ 3) и маркировка "potential" для утверждений без evidence — требования сценария; конкретные HTTP-статусы, максимальный размер diff и SLA — отсутствуют в источниках и отмечены как открытые вопросы.

## Что изменили в исходном артефакте

- Файл и раздел:
  - practices/practice_01/product_management.md → раздел «User stories и acceptance criteria».
- Изменение:
  - добавлены три Gherkin-сценария для помощника ревьюера PR по unified diff (позитивный, негативный, граничный),
  - уточнена структура отчёта: «Описание», «Риски» (≤ 3 пункта), «Проверки»,
  - evidence для каждого пункта «Рисков»: путь к файлу и координаты хунка или точный фрагмент хунка; координаты не путать с номерами строк исходника,
  - утверждение без достаточного evidence обозначается как «потенциальный риск/гипотеза» или «неизвестно/вопрос»,
  - негативный сценарий фиксирует факт отсутствия поля diff как ошибку, без придумывания HTTP-статусов.
- Как проверили:
  - product_management.md и tests_e2e.md синхронизированы (три сценария отражены в обоих файлах);
  - выполнена команда проверки: make -C practices/practice_02 test → «Practice 2 artifacts: OK».
- Что отклонили:
  - результат про авторизацию отклонён как не относящийся к выбранному артефакту и содержащий выдуманные требования (5 попыток, 15 минут, LOGIN_*).
  - уточнения по принятым правкам: ограничение «≤ 3 пункта» относится только к разделу «Риски»; отчёт обязан содержать разделы «Описание», «Риски», «Проверки»; утверждения без достаточного evidence называем «потенциальный риск/гипотеза» или «неизвестно/вопрос»; evidence должен включать путь и координаты/фрагмент хунка, без подмены координат номерами строк исходника.
