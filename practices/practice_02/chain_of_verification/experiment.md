# Chain of Verification

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- Проверяемый черновик или утверждение:
  Текущие позитивный, негативный и граничный Gherkin-сценарии из раздела «User stories и acceptance criteria» файла practices/practice_01/product_management.md.
## Запрос на проверку

"Chain of Verification for PR-review assistant

Draft:
- Кратко выпиши проверяемые утверждения текущих трёх сценариев из practices/practice_01/product_management.md.

Verify:
- Сформулируй отдельные вопросы проверки:
  1) подтверждает ли practices/practice_01/TRAINING_PR.diff ошибку при отсутствии поля diff;
  2) существует ли в реализации контролируемая валидация входа;
  3) реализована ли проверка формата unified diff;
  4) реализовано ли ограничение не более трёх рисков;
  5) подтверждён ли формат evidence (путь и координаты хунка @@ -x,y +u,v @@ или точный фрагмент);
  6) определено ли правило выбора трёх кандидатов;
  7) подтверждено ли поведение для утверждений без evidence (не включать в «Риски», добавлять в «Проверки»);
  8) согласованы ли practices/practice_01/product_management.md и practices/practice_01/tests_e2e.md.

Check:
- Для каждого вопроса укажи конкретный источник (из списка разрешённых) и один статус: «подтверждено реализацией», «принятое требование TO BE», «не подтверждено» или «противоречие».

Final:
- Верни исправленную версию трёх Gherkin-сценариев, где факты AS IS, требования TO BE и открытые вопросы явно разделены в комментариях. Удали утверждения, для которых нет ни evidence, ни принятого требования."

## Исправленный результат

```gherkin
Feature: Помощник ревьюера PR по unified diff

  # Комментарии помечают статус: AS IS (факт реализации), TO BE (принятое требование), OPEN (открытый вопрос)

  Scenario: Позитивный — корректный unified diff → структурированный отчёт
    # TO BE: минимальные признаки корректного unified diff — заголовки файлов и ≥ 1 хунк изменений
    Given на вход передан unified diff с заголовками файлов и хотя бы одним хунком изменений
    When помощник анализирует diff
    Then полный отчёт содержит разделы: "Описание", "Риски" (не более 3 пунктов) и "Проверки"  # TO BE
      And каждый пункт раздела "Риски" содержит evidence: путь к файлу и координаты из заголовка хунка @@ -x,y +u,v @@ или точный фрагмент хунка  # TO BE
      And координаты хунка не выдаются за номера строк исходного файла  # TO BE

  Scenario: Негативный — отсутствует поле diff в payload
    # AS IS: обращение к payload["diff"] без поля приводит к ошибке до формирования отчёта (TRAINING_PR.diff, app/api.py)
    # TO BE: запрос должен отклоняться контролируемо до анализа; формат ответа и HTTP-статус — OPEN
    Given входной объект не содержит поля "diff"
    When инициируется анализ
    Then отчёт не формируется; анализ прекращается до формирования отчёта  # AS IS/TO BE согласовано
      And формат ответа и HTTP-статус остаются открытыми вопросами  # OPEN

  Scenario: Граничный — найдено > 3 кандидатов и часть утверждений без evidence
    Given на вход передан unified diff с хотя бы одним хунком изменений  # TO BE
      And по результатам анализа найдено более трёх кандидатов в риски  # TO BE
      And часть утверждений не имеет достаточного evidence в diff  # TO BE
    When помощник формирует итоговый отчёт
    Then раздел "Риски" содержит не более трёх пунктов с наиболее сильным evidence в diff  # TO BE
      And утверждения без достаточного evidence не включаются в раздел "Риски", а добавляются как предлагаемые проверки в раздел "Проверки"  # TO BE
      And evidence для каждого пункта "Рисков" содержит путь к файлу и координаты хунка или точный фрагмент этого хунка  # TO BE
```
## Что изменили в исходном артефакте

- Файл и раздел:
  - practices/practice_01/product_management.md → после блока Gherkin добавлен раздел «Статус проверки требований» с таблицей статусов.
  - practices/practice_01/tests_e2e.md → без изменений (проверка подтвердила согласованность с product_management.md).
- Изменение:
  - Добавлена таблица статусов (AS IS, TO BE, неподтверждённое) для ключевых утверждений: ошибка при отсутствии diff, контролируемая валидация отсутствующего diff, проверка формата unified diff, структура отчёта, формат evidence, исключение утверждений без evidence из «Рисков».
- Что отклонили:
  - Не выдавать контролируемую валидацию и проверку формата diff за реализованные функции: они зафиксированы как требования TO BE/открытые вопросы, а не как реализованные факты.

Скрытые рассуждения модели не сохраняйте; нужны только вопросы, подтверждения и исправленный результат.
